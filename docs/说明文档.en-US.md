# CodePilot Overview

Language: [简体中文](说明文档.zh-CN.md) | English

## 1. Positioning

CodePilot is a workflow orchestration CLI for local engineering repositories. Its core goal is to standardize the flow from "requirement -> clarification -> plan -> task -> execution -> review -> operations -> release".

Current version: `0.7.2`

Core capabilities:

- Natural-language entry points: `codepilot "requirement"`, `go`, `chat`, Web UI, and Feishu.
- Pre-execution shaping: `clarify` generates requirement specs, and `plan` generates reviewable execution plans.
- Read-only evidence gathering and knowledge capture: `explore`, `wiki`, `note`, and `trace`.
- Task lifecycle management through the unified `task ...` subcommands.
- Project queue and background services: `run`, `daemon`, `inspect`, and `ui`.
- Integrations: Feishu long-connection bot, Webhook, event sink, Hook registry, and Provider smoke tests.
- AI-friendly interfaces: `ai manifest`, `ai guide`, `ai template`, and `--json` output for common commands.
- Binary build and release through the unified `binary ...` subcommands.

## 2. Architecture Overview

Logical layers:

1. CLI entry layer: `codepilot/cli.py`, `codepilot/commands/*`
2. AI and planning layer: `codepilot/ai_support/*`, `codepilot/prompts/*`
3. Execution and runtime layer: `run`, `daemon`, `inspect`, `build-fix`
4. Data layer: SQLite projects, tasks, logs, sessions, and service status
5. Interaction layer: terminal output, local Web UI, Feishu, and Webhook
6. Integration layer: event sink, Hook registry, Provider exec, and Skill catalog

Main directories:

- `codepilot/`: core implementation
- `codepilot/commands/`: CLI subcommands
- `codepilot/web/`: Web UI frontend assets
- `codepilot/webapp/`: Web UI server actions and payloads
- `codepilot/templates/`: task templates
- `docs/`: Chinese overview and operation docs
- `skills/`: reusable Agent Skills
- `tests/`: pytest tests

## 3. Command Domain Model

### 3.1 Entry Points and Requirements

- `codepilot "requirement"`: top-level plain-text entry point, suitable for submitting clear one-off requirements.
- `go`: explicit natural-language entry point that can process requirements or answer project and task questions.
- `chat`: OpenCode TUI continuous-session entry point, suitable for ongoing Q&A, task operations, and workflow execution.
- `auto`: splits high-level goals into tasks, with an option to plan only.
- `add`: low-level entry point for external AI or automation systems to submit pre-planned tasks directly. It is not intended for routine manual use.

### 3.2 Clarification, Planning, and Read-Only Evidence

- `clarify`: generates a pre-execution requirement spec without creating tasks or executing code.
- `plan`: generates a reviewable execution plan without creating backlog items or starting the executor.
- `explore`: performs read-only exploration of project files, Git, tasks, wiki, and inspect signals.
- `wiki`: maintains the local project Markdown knowledge base.
- `note`: maintains persistent project working memory.
- `trace`: shows the timeline for tasks, logs, service heartbeats, and workflow state.

### 3.3 Tasks and Execution

- `status` / `hud`: view the task board and lightweight workspace state.
- `task show/logs/find/edit/stop/retry/resume/cancel/archive/done/rm/sweep`: full task lifecycle operations.
- `run`: executes the project backlog.
- `daemon`: continuously polls and executes the backlog in the background.
- `build-fix`: runs a failed-task loop of "failure collection -> retry repair -> verification -> verdict".

### 3.4 Services, Integrations, and Release

- `inspect`: inspects project signals and produces candidate tasks.
- `ui`: starts the Web UI in the foreground or manages the background service.
- `feishu`: Feishu enterprise app long-connection bot.
- `webhook`: HTTP `/tasks` submission entry point.
- `event`: local project event sink registry.
- `hook`: project-level hook wrapper planning, validation, and testing.
- `exec`: provider command smoke test and audited execution inside the project.
- `skill`: local project Skill catalog management and execution.
- `binary`: build, install, release, and verify the platform binary.
- `doctor`: environment, configuration, database, and service health checks.

## 4. Execution Boundaries

Hard constraints:

- Task operations must use `codepilot task ...`.
- Releases must use `codepilot binary ...`.
- Web UI services must use `codepilot ui ...`.
- The legacy top-level `release` entry point, top-level `show/logs/stop/retry/find/...`, and the legacy `webui` entry point have been removed.
- `chat`, Web UI sessions, and Feishu free text are routed to OpenCode + CodePilot MCP. Use `clarify`, `plan`, or the corresponding panel/MCP tool explicitly when a structured spec or plan is required.
- Inputs about project status, task counts, completion ratio, failed tasks, running tasks, service status, and similar topics are handled as Q&A by default.
- `explore`, `clarify`, and `plan` do not execute code, start services, or write business files by default.

## 5. Configuration and State

Main configuration file: `AGENTS.toml`

Common configuration areas:

- `[project]`: project identifier, default mode, and baseline branch
- `[automation]`: planner, executor, and auto-execution strategy; `fallback_cli_order` determines the text-mode CLI fallback order, defaulting to `["claude", "codex", "opencode"]`; `agent_language = "en" | "zh-CN"` controls agent-facing prompts, task template content, and the preferred output language. The default is English.
- `[inspect]`: inspection policy
- `[agents]` and `[agents.commands]`: planner/builder/reviewer defaults plus CLI family command mappings for claude/codex/opencode. The old scalar `codex_cmd` / `claude_cmd` fields have been removed; loading them raises `ConfigError` with a migration example.
- `[feishu_bot]`: Feishu long-connection bot
- `[notifications]`: task status notification webhook
- `[automation.scheduled_agents.<name>]`: scheduled agent. Required fields are `agent` and `prompt`; configure either `interval = "10m"` / `"1h"` / `"1d"` or a five-field `schedule = "0 9 * * *"`.
- `[automation.event_agents.<name>]`: event agent. Required fields are `trigger`, `agent`, and `prompt`; the event stream currently matches `trigger` and creates `agent_job` entries.

Put sensitive information in `.codepilot.secrets.toml` and do not commit it to the repository.

### 5.1 Scheduled / Event Agent Configuration

Minimal example:

```toml
[automation.scheduled_agents.task_health]
enabled = true
agent = "codex"
interval = "10m"
prompt = "Review local CodePilot task status and summarize risks."
max_cost_usd = 0.10
max_daily_cost_usd = 0.50

[automation.event_agents.failed_task_triage]
enabled = false
trigger = "task.failed"
agent = "codex"
prompt = "Task {{ task_id }} failed with {{ error_message }}. Suggest the smallest repair."
max_cost_usd = 0.10
max_daily_cost_usd = 0.50
```

Scheduled agents can be inspected and manually verified with:

```bash
codepilot scheduled list -p <project-name>
codepilot scheduled show task_health -p <project-name> --json
codepilot scheduled run-once task_health --dry-run
codepilot scheduled run-once task_health -p <project-name> --dry-run
codepilot scheduled disable task_health -p <project-name>
```

The repository provides three scheduled agents by default:

- `task_health`: checks task state, failed tasks, long-running in-progress tasks, and recent scheduler audit records; it only outputs risk summaries and conservative check suggestions.
- `daily_summary`: prepares a project daily-summary draft. Only when Feishu is configured can downstream flows use the summary for Feishu delivery; the agent itself does not send messages directly.
- `auto_inspect`: creates a lightweight inspection plan and actionable findings from existing inspect signals, and is required to avoid direct code changes.

Supported event-agent event types depend on event producers. Templates can read fields from the event `payload`; built-in task failure events use flat fields such as `{{ task_id }}` and `{{ error_message }}`. Feishu-related events require `[feishu_bot]` to be configured and `codepilot feishu start` to be running. MCP tool injection depends on the corresponding agent CLI and MCP launcher capability, so unconfigured MCP or Feishu capabilities should not be documented as guaranteed.

### 5.2 Audit, Cost, and Loop Protection

Each scheduled / event agent execution or dry-run appends one JSON line to `.codepilot/scheduled/audit.jsonl`. The prompt text is not stored; only `prompt_hash` is saved. Main fields:

- `timestamp`: audit record time.
- `trigger`: trigger source, such as `manual`, `interval`, `schedule`, or `event`.
- `project`, `job_name`, `agent`: project, agent config name, and CLI family.
- `prompt_hash`: SHA-256 digest of the prompt, used for tracking without exposing content.
- `tools`, `token_usage`, `cost`, `exit_code`: execution metadata; these are usually empty, zero, or `null` during dry-run.
- `agent_chain`: cross-agent trigger chain for loop protection.
- `guard`, `notification`, `dry_run`: guard state, notification payload, and whether the run was a dry-run.

Cost guard behavior:

- `max_cost_usd` limits cost per call. If parsed `cost` exceeds the limit after execution, the result is marked as `guard.status = "tripped"` and the audit record uses `reason = "max_cost_per_call"`.
- `max_daily_cost_usd` limits daily accumulated cost for one `project:name`. After the limit is exceeded, `.codepilot/scheduled/guards.json` is written and the agent is disabled; later executions are skipped with `reason = "disabled"`.
- The internal runner also supports `max_tokens_per_call`. When exceeded, the record uses `reason = "max_tokens_per_call"`; the current AGENTS configuration parser exposes the cost fields.

Loop circuit breaker rules:

- Each job forms an `agent_chain`; the current job key format is `<project>:<name>`.
- When chain depth exceeds 5, no external CLI is called. The run is audited directly as `guard.status = "skipped"` and `reason = "loop_circuit_breaker"`.
- Running `codepilot scheduled disable <name> -p <project-name>` manually marks the agent as disabled in `guards.json`. Later dry-runs and real executions are skipped during preflight.

Manual validation commands for documentation and configuration changes:

```bash
pytest tests/test_scheduled_*
codepilot scheduled run-once task_health --dry-run
codepilot scheduled run-once task_health -p codepilot-dev --dry-run
```

### 5.3 OpenCode-Specific Mode

CodePilot does not modify OpenCode source code by default. Before `codepilot chat -a opencode` starts, it writes and injects three kinds of official configuration:

- `OPENCODE_CONFIG` -> `~/.codepilot/opencode/<project-id>/opencode.json`: CodePilot MCP, default agent, commands, instructions, permission, and tools.
- `OPENCODE_TUI_CONFIG` -> `~/.codepilot/opencode/<project-id>/tui.json`: TUI theme, scroll, diff, mouse settings, and the CodePilot-branded TUI plugin.
- `OPENCODE_CONFIG_DIR` -> `~/.codepilot/opencode/<project-id>/config`: native OpenCode `agents/`, `commands/`, `instructions/`, and `tui-plugins/codepilot-brand.tsx` files.
- `OPENCODE_DISABLE_TERMINAL_TITLE=1`: disables OpenCode's own terminal title updates, so CodePilot sets the terminal window/tab title to `brand_name`.

The OpenCode wrapper branding, TUI, Chinese interaction rules, default agent, and built-in commands are CodePilot tool-level customizations and ship with the package. Business projects do not need, and should not add, `[opencode.profile]`, `[opencode.agent]`, or `[opencode.commands]` to `AGENTS.toml` just to use this tool. Business project directories do not receive `.codepilot/opencode/`; runtime files are written only to user-level `~/.codepilot/opencode/<project-id>/`, where they store the current project registration name, MCP launch config, isolated OpenCode session data, and project-level model selection.

Business projects can configure runtime policy:

- `[agents.commands].opencode`: selects the official OpenCode command or local development command to use.
- `[providers.<name>]`: configures OpenAI, DeepSeek, Qwen, Kimi, Gemini, Claude, or another OpenAI-compatible provider. CodePilot dynamically generates OpenCode providers by provider name and does not pack every custom model into the `openai` category.
- `[opencode.permission]`: configures the current project's OpenCode permission mode. Supported values are `ask`, `full_access`, and `custom`.

Model selection persistence:

- After a user switches models in the OpenCode TUI, CodePilot syncs that selection from the isolated OpenCode session database.
- New sessions in the same project prefer the project-level model saved by CodePilot.
- If no project model has been saved, OpenCode's built-in free default model does not override the provider/model configured for the project.

Permission layering:

- OpenCode uses `permission` as the first layer and sets `bash`, `edit`, `write`, and `webfetch` to `ask` by default.
- For trusted projects, set `[opencode.permission] mode = "full_access"` in `AGENTS.toml` to skip OpenCode permission prompts.
- For fine-grained rules, set `mode = "custom"` and configure `bash`, `edit`, `write`, `webfetch`, and other rules under `[opencode.permission.rules]`.
- CodePilot MCP tools keep their own secondary checks. For example, `exec` only allows allowlisted commands, and task/Feishu/Webhook/hook entry points validate their own tool arguments and project context.

Official OpenCode mode only requires `[agents.commands].opencode = "opencode"`. There is no source-code path that can override terminal window/tab title, homepage logo, sidebar title, or footer. This project does not maintain an OpenCode source overlay or a custom binary. If other hardcoded welcome text or permission prompt text inside the OpenCode TUI still says OpenCode, treat it first as an official-binary configurability boundary.

Manual smoke test:

```bash
codepilot chat -a opencode
```

Expected result: CodePilot MCP startup feedback appears, then the OpenCode TUI starts, and CodePilot MCP task/status commands are available.

Exit experience:

- The startup transition page uses a temporary terminal screen. Before entering OpenCode, it exits the temporary screen and does not write to the main terminal history.
- After OpenCode exits, CodePilot prints only a compact resume hint instead of clearing the entire terminal.
- The resume command is `codepilot chat --session <session_id>` and continues to use CodePilot's isolated configuration, MCP, and session data.

Database-persisted content:

- Project registration information
- Tasks, dependencies, status, logs, and delivery records
- Sessions, workflow state, and service heartbeat
- Event sink, wiki, note, Skill catalog, and other project-level state

Common task states:

- `backlog`
- `in_progress`
- `done`
- `failed`
- `cancelled`
- `archived`

## 6. External Integration

Recommended entry points:

- Non-interactive requirements: `codepilot "requirement"`
- Q&A: `codepilot go "What is the current project status?" -p <project-name>`
- Structured collection: `status --json`, `hud --json`, `task show --json`, `task find --json`, `trace --json`, `doctor --json`
- Standard command description: `codepilot ai manifest`
- Feishu long connection: `codepilot feishu start`
- External task submission: `codepilot webhook --host 127.0.0.1 --port 8765`
- External AI direct task submission: first read `codepilot ai template --format json`, then submit template-compliant content

## 7. Version Changelog

The version grouping is based on consecutive feature batches in Git history. Missing early historical tags have been backfilled into semantic versions by capability boundary. During the `0.x` stage, minor versions may include entry-point changes and configuration migrations.
